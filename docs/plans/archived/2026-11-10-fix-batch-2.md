# Fix batch 2, 2026-11-10: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close #43, #44, #42 and #41, the open issues an agent can finish.

**Architecture:** One task per issue, test first, where the issue points.
Tasks 2 to 4 all change the compositor (`src/sqlearn/_compose.py`) and run in
this order: the refusal (Task 2) guards the marker arguments Task 3's new
variance marker also takes, and Task 4 restructures the learn stage last.
No new public API.

**Tech Stack:** Python 3.12+, DuckDB 2.x, pytest, uv, just.

**Spec:** each issue's body is the spec of its task (`gh issue view N`), read
with `docs/specs/library-preprocessing.md`, ADR 0036 (staged aggregates
anywhere in a learned value) and ADR 0044 (the two-pass standard deviation).

## Global Constraints

- Computation is SQL run by DuckDB; Python is the glue (ADR 0002). No row
  loops in Python over the data.
- The only runtime dependency is `duckdb` (ADR 0004).
- Every refusal is a `SqlearnError` (or `StepError`) in the house form: what
  happened, why, then `Fix:`. No raw DuckDB error reaches the user for a case
  a task covers.
- Floating-point results are compared within a bound, never byte for byte
  (ADR 0043). `just verify` rewrites `validation/**/*.results.json`: keep
  those diffs only where the task changes the validation.
- Test names use `GLOSSARY.md` terms and read as sentences; tests go through
  public seams (`sq.*`, `Pipeline`) unless the issue names a private function.
- British English in prose, American spelling in identifiers (ADR 0010).
- Commits name their issue: `fix: ... (#N)` or `perf: ... (#N)`. No AI
  attribution anywhere.
- Before each commit: `just fmt`, `just check`, `just test`. Before the
  branch is called done: `just verify`, and the docs rebuilt clean
  (`rm -rf docs/reference/generated docs/_build && just build-docs`).

## Review Focus

1. An ENUM column whose values a later batch does not hold, through onehot
   and ordinal: the codes and columns still follow the learned categories.
   Task 1 tests an apply on data holding a subset of the ENUM's values.
2. A plain aggregate inside any staged marker, not only std:
   `sq.agg.median(x - sq.agg.mean(x))` must be refused the same way. Task 2
   tests median, mode and std.
3. `var` and `std` of the same column in one step: one pair of passes, and
   `std` still `sqrt` of exactly that variance. Task 3 tests the stage count
   and the values.
4. A step learning both a whole marker and a marker nested in an aggregate
   (`{"m": median(x), "d": mean(abs(x - median(x)))}`) after Task 4: both
   values unchanged. Task 4 tests it.
5. A target encoder on several columns in one step after Task 4: each
   column's stats still go to its own learned value. Task 4 tests two
   columns.

- Docs: `docs/adr/0044-the-standard-deviation-in-two-staged-passes.md` and

**Interfaces:**

- Consumes: `_in_aggregates(text) -> list[tuple[int, int]]` (finds plain

- Produces: the rule Task 3 inherits: a staged marker's argument may hold

The issue allows learning it or refusing it; refuse. `std(x - mean(x))` is
`std(x)`, and staging arbitrary aggregates is compositor code nobody needs.

- [ ] **Step 1: Write the failing tests**:
  `test_a_plain_aggregate_inside_a_standard_deviation_is_refused`
  (`sq.agg.std(x - sq.agg.mean(x))`), and the same for `sq.agg.median` and
  `sq.agg.mode`. Each asserts a `StepError` whose message names the step
  and position and contains "a plain aggregate" and "Fix:", and no
  "Binder Error".
- [ ] **Step 2: Run them and watch them fail** with today's
  "DuckDB failed, and no step could be named".
- [ ] **Step 3: Implement**: in `reference` (every marker's arguments, after
  the inner markers are set aside) and in `_std` (the text after inner
  markers are replaced by their plain columns), refuse when
  `_in_aggregates` finds a call. Why: "a plain aggregate inside a staged
  one, which is computed per row of the stage's input, where one value of a
  whole column has no row." Fix: "learn the inner aggregate in an earlier
  step, or leave it out: the spread of x - mean(x) is the spread of x."

### Task 4: The learn stage reads a whole staged value once (#41)

**Files:**

- Modify: `src/sqlearn/_compose.py` (`_learn_ctes`, `:1175-1225`;
  `_std_ctes`' `rows`), the module docstring's sentence on cross-joining
- Modify: `docs/benchmarks/category-lookup.md` (the target encoder's learn
  times, new beside old)
- Test: `tests/src/sqlearn/test__compose.py`,
  `tests/src/sqlearn/preprocessing/test_target.py`
- Docs: ADR 0036 "Amended by #41"

**Interfaces:**

- Consumes: `_Staged.reference(stage, text, marker, nested=True)`: the plain
  column of a marker's one-row stage (Task 3's `sqrt(v<i>)` for std).

Today every one-row stage is cross-joined into the learn stage's scan of the
previous stage, so each source row carries the target encoder's whole stats
list (19 of 26 s at 200k rows). The change:

- A learned value whose whole text is one staged marker (the target
  encoder's `stats`, a bare `median(x)`, `std(x)`) is not computed in the
  scan. It is read in an outer select over the scan's one row, cross-joined
  with that marker's one-row stage, as the plain column.
- The scan cross-joins only the one-row stages that some other reference
  (nested, or inside a larger expression) reads. With none, it reads the
  previous stage alone.
- The standard deviation's passes cross-join only the stages their
  expressions read, not every earlier one.
- The learn stage keeps its name, its columns' names and order, and
  `MATERIALIZED`.

- [ ] **Step 1: Write the failing test**
  `test_the_learn_scan_does_not_carry_a_whole_staged_value`: the SQL of a
  pipeline with `sq.encode.target()` (`sq.Pipeline.describe` or the
  compositor's `build`) has no `CROSS JOIN` of the `_stats` stage inside
  the scan of the previous stage. Assert on the SQL text, the only seam that
  shows it.
- [ ] **Step 2: Run it and watch it fail.**
- [ ] **Step 3: Add the value-preserving tests** (they pass before and after):
  two target-encoded columns in one step (Review Focus 5), and one step
  learning `{"m": median(x), "d": mean(abs(x - median(x))), "r": max(x) -
  median(x)}` (Review Focus 4), each against hand-computed values.
- [ ] **Step 4: Implement** as above.
- [ ] **Step 5: Run the whole suite**, then `uv run python -m validation`:
  the target encoder's and the aggregates' results are identical to `main`'s
  within ADR 0043's bounds.
- [ ] **Step 6: Measure**:
      `uv run python -m validation.benchmarks.category_lookup` (write its data
      to Parquet first if memory is short, as HANDOFF warns). Add the target
      encoder's new learn times at 100, 1,000 and 10,000 categories beside the
      old ones (46.8 s at 10,000) in `docs/benchmarks/category-lookup.md`, and
      say what remains (the Python `Fraction` arithmetic, about 5 s at 200k
      rows, is not in this task). If the learn time at 10,000 categories does
      not fall well below the old, stop and report before committing: the
      hypothesis was wrong.
- [ ] **Step 7: Commit**
      `perf: read a whole staged value once in the learn stage (#41)`.
